# Console translation

The console is translated with a small in-house layer in `src/i18n/` — no
runtime dependency. English is the source; French is the first translation.

## How it works

- `en.ts` holds every translated string under a stable key (`nav.storage.label`,
  `settings.save…`). Its keys are the `MessageKey` type.
- `fr.ts` is typed `Record<MessageKey, string>`: a key missing from it fails
  `npm run typecheck`, so a half-translated screen cannot ship.
- Components read strings with `const { t } = useI18n()` and `t('some.key')`.
  Placeholders are `{name}`: `t('key', { name: 'x' })`. A translation keeps the
  same placeholders as English (checked by `src/i18n/i18n.test.ts`).
- The language is the saved choice (`localStorage`, key `hearthrack.locale`),
  else the first supported browser language, else English. `<html lang>`
  follows it.
- Navigation data (`NAV` in `App.tsx`) stores message keys, not text, so the
  sidebar, page title and tabs switch language together.

## Translating a screen

1. Move each user-visible string to `en.ts` under `<screen>.<what>`.
2. Replace it with `t('<screen>.<what>')`; compute any module-level text lazily
   (store the key, call `t` at render).
3. Add the French in `fr.ts`.
4. Leave out of the catalogue what is data, not wording: resource names, CR
   kinds, units, log lines, API error text.

Dates and numbers should go through `Intl` with `useI18n().locale`, not
hand-built strings.

## Adding a language

Create `<code>.ts` next to `fr.ts` (typed `Record<MessageKey, string>`), then add
it to `CATALOGUES` and `LOCALES` in `src/i18n/index.ts`.
